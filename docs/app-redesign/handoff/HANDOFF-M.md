## For the device pass (CI-only code paths, not provable in the harness) — WP-INT: treat the first item as a gate

- **Gate:** the report WebView (an `AndroidView`; shared elements do not support View interop in the overlay). It is never drawn in the overlay, either way: content alpha 0 while the bounds move (the container carries the report's cover, `drawReportCover`), then a 150 ms fade in place once they settle. Check on a phone: (1) no flash, blank or stale WebView frame when a History/Research row opens its report and when back closes it into the row (also a held back gesture then a commit); (2) the WebView survives (no reload when the report is reopened from the stack, scroll kept); (3) **at rest** the report and tab layers always sit inside the shell's `SharedTransitionLayout` (a `LookaheadScope`, so an extra lookahead measure pass): the report WebView scrolls and lays out normally, with no blank frames on resize, rotation or IME show/hide, and frame time on History, Research and the report itself does not regress against PR-4a (Profile GPU rendering or `adb shell dumpsys gfxinfo`). If (3) fails, move `ReportBaseLayer` out of `ShellTransformScope` (wrapping the scope only around a running transform would recompose, and so reload, the WebView) and drop the report's transform; Name's stays.
- If the device pass shows the WebView does draw correctly in the overlay, the report can follow Name exactly: content on `transformContentAlpha(reveal)` in and `transformContentAlphaOut(clock)` out (`ReportBaseLayer`, `contentIn`), and the cover can go.
