# Phase 7 M2 review

## Scope

Reviewed the Phase 7 M2 milestone brief and evidence, the current working tree implementation under `apps/product-api/src/pulse/`, the dispatch/persistence path in `apps/product-api/src/server.ts` and `apps/product-api/src/store.ts`, the M2 contract and Product API tests, and the later Phase 7 roadmap milestones.

M2's customer-facing renderer is no longer the current product surface: the Phase 7 roadmap says M7 replaced the old renderer with the newspaper hierarchy and M8 replaced the customer-facing export with the Morning Brief structure. M2's additive editorial issue and its sections are still generated by `buildMarketPulseReport`, and the current issue plan still consumes M2 editorial fields, so the data-path findings below remain relevant.

## Findings

### P2 — Historical/replayed dispatch can compare against a future Pulse

`fintech/apps/product-api/src/server.ts:5344-5349` obtains `getLatestReportByType("market_pulse")` without constraining it to a report whose `created_at`/`cycle_end` precedes the job's `cycleEnd`. Both store implementations sort all reports descending and return the first (`fintech/apps/product-api/src/store.ts:2646-2650` and `4998-5006`). The selected artifact is passed as `previousReport` to the editorial builder.

Trigger: dispatch a fixed historical cycle after a newer Pulse already exists, or run a delayed/replayed cycle while a later cycle is the latest stored report. Impact: M2's `prior_cycle_end`, `what_changed`, `freshness_state`, and “yesterday” copy can describe the later report; a replay can therefore use future context and produce a false daily delta. This violates the milestone's prior-Pulse comparison semantics for replayed cycles and the Phase 7 replay-safe data policy. Evidence is direct from the unbounded latest-report query and call site; no test covers an out-of-order or historical dispatch.

### P2 — Daily tape changes are reduced to a four-state breadth bucket

`fintech/apps/product-api/src/pulse/editorial-issue.ts:74-83` declares `nothingMaterialChanged` true whenever breadth, macro state, sector leader, VIX threshold regime, and calendar-event presence are unchanged. `tapeBreadth` (`fintech/apps/product-api/src/pulse/common.ts:81-95`) only counts index directions; it ignores the magnitude and identity of moves. Therefore a large move in all core indices that remains `higher` (or `lower`/`mixed`) is rendered as “No material change from yesterday's issue” (`editorial-issue.ts:85-89`) unless one of the unrelated flags changes.

Trigger: keep the same number of up/down core indices while changing their `daily_change_pct` materially between two reports. Impact: the M2 daily delta and lead suppress a real market-tape change, and `signal_vs_noise`/watch copy can incorrectly present a quiet issue. The implementation and tests cover a breadth-state transition, but do not cover same-breadth/magnitude-change or changed-index-identity cases.

## Tests reviewed and run

Reviewed the M2 evidence in `Project Note/Phase7/Milestones/M2/evidence/2026-04-26_m2_editorial_freshness_verification.md`, `apps/product-api/tests/market-pulse.test.ts`, `apps/product-api/tests/market-pulse-render.test.ts`, and `packages/contracts/tests/market-pulse-report.test.ts`. The recorded evidence reports 15 contract tests, 95 Product API tests, focused dispatch/render tests, and 24 data-openbb unittest cases passing; pytest was unavailable in that environment. I did not rerun the full suites because the parent review is already running the worker/API suites.

The reviewed tests prove baseline creation, prior-cycle delta for the fixture scenario, calendar watch items, calendar degradation, contract optionality, and rendering. They do not exercise (1) a replay whose latest stored report is in the future relative to the requested cycle, or (2) a same-breadth tape with materially different move magnitudes/identities.

## Gaps and verdict

No P1 issue was established from the reviewed code and evidence. The two P2 findings should be fixed if M2's editorial data path remains supported. The M2-specific renderer proof is historical and should not be treated as a current export acceptance gate because M7/M8 superseded that surface; current validation should target the M7/M8 issue-plan and Morning Brief output while retaining the underlying replay and delta correctness requirements.

Verdict: **M2 not fully correct in the current working tree; conditional pass only for the documented, later-superseded renderer surface.**
